# Ideal 注入策略指南（Ideal Injection Guide）

本指南定义了如何将 Ideal 文档（代码分析产出）的内容按**阶段差异化策略**注入到专利撰写的各个环节。不同阶段使用不同的注入强度和格式，以最大化利用 Ideal 中的技术信息。

---

## 概述

Ideal 文档是 Stage 01-02（代码分析）的产出，包含从代码仓库中提取的创新点、技术方案、量化数据、应用场景等结构化信息。在后续专利撰写的各个 Stage 中，需要将 Ideal 内容按**不同强度**注入：

| 阶段类型 | 对应 Stage | 注入强度 | 策略 |
|---------|-----------|---------|------|
| 探索阶段（发明范围、关键术语、发明构思） | 03, 06, 07 | 🟢 软引导 | 作为参考，不局限于此 |
| 检索阶段（现有技术分析） | 04 | 🔵 双语扩展 | 中英双语关键词，扩展检索广度 |
| 文献检索阶段（联网文献收集） | 05 | 🔵 双语检索注入 | 从 Ideal 提取中英文检索关键词，生成跨语言检索 query |
| 写作阶段（背景技术、发明内容） | 08, 09 | 🔴 强制约束 | 必须优先围绕这些主题展开 |
| UI 截图阶段（产品侧 UI 原型与截图） | 10 | 🔴 强制约束 | 从 Ideal 提取产品交互描述，强制生成页面原型并截图 |
| 评审阶段（专利评审） | 12 | 🟡 对照清单 | 检查是否充分覆盖 |
| 修订阶段（专利修订） | 13 | 🟠 保护性+素材库 | 不要弱化或遗漏 + 提供修订素材 |
| 质量门禁（质量评估） | 14 | 🔴 阻断级 | 任一不满足则判定需修订（含图文完整性检查） |

---

## 一、注入前：文本消毒

**所有注入前必须执行消毒**，移除以下内部标记：

```
[代码参考: xxx]  → 删除（此标记仅在 Ideal 文档内部使用，不应出现在专利正文中）
[ref: func_name]               → 删除
[推断] / [估算] / [inferred]   → 删除
[file: path/to/file.py, ...]   → 删除
[N/A]                          → 删除
`_func_name()`                 → 删除（裸露的代码标识符）
```

消毒后压缩连续 3+ 空行为 2 行，清除行尾空白。

## 二、11 种注入策略详解

### 策略 1：通用写作注入（强制）

**适用 Stage**：背景技术（Stage 08）、发明内容（Stage 09）

**注入语气**：「必须优先围绕这些主题展开，确保这些创新点在文档中得到充分表达」

**注入内容**：消毒后的完整 Ideal 文本

**创新点举证强制约束**（Stage 09 专用，最高优先级）：
1. **独立举证段落**：发明内容的 4.2.2 核心算法流程中，每个经过 Round 1.5 筛选保留的核心创新点（2-3 个），必须有**至少一个完整的 S 步骤**专门为其提供技术方案举证，而不是在一个泛化步骤中混合多个创新点
2. **举证充分性**：每个创新点的举证步骤必须完整包含 6 个子段（问题动机、技术动作、输入数据样例、输出数据样例、关键参数、白话解释），缺少任何子段视为举证不充分
3. **禁止重复性描述**：4.2.3（模块间交互时序）和 4.2.4（数据流描述）必须提供独立于 S1-SN 的新视角，不得重复已在算法步骤中描述的内容
4. **场景深度对等**：4.1 产品侧的场景二描述深度必须与场景一对等，每个步骤不少于 80 字

### 策略 2：探索软引导

**适用 Stage**：发明范围（Stage 03）、关键术语（Stage 06）、发明构思（Stage 07）

**注入语气**：「作为参考，但不要局限于此」

**注入指引**：
1. 先独立、全面地分析技术领域现状和问题
2. 在此基础上，结合发明人的思路，识别有价值的创新切入点
3. 如果分析过程中发现比发明人思路更优的方向，也应一并指出

### 策略 3：检索双语扩展

**适用 Stage**：现有技术分析（Stage 04）

**注入内容**：中文原文 + 英文关键词/概念提取

**注入指引**：
1. 以这些方向为**核心**生成搜索关键词
2. 同时扩展至相关技术领域，确保检索的**广度**
3. 注意同时生成中文和英文搜索关键词

**英文提取方法**：不做全文翻译，只提取有学术检索价值的英文术语和核心概念（节省 token）

### 策略 3.5：文献检索双语注入（强制）

**适用 Stage**：联网文献收集（Stage 05）

**注入强度**：🔵 双语检索注入

**注入内容**：从 Ideal 文档中提取：
1. **中文检索关键词**：从创新点名称、技术领域描述、现有技术名称中提取
2. **英文检索关键词**：从双语术语映射表、英文技术术语中提取
3. **专利分类号建议**：从 Ideal 中的技术领域描述推断适用的 IPC 分类号

**注入模板**：
```
你现在需要通过联网检索获取真实的现有技术文献。

以下是基于发明创新方向提取的检索关键词：

中文检索词：{ideal_cn_keywords}
英文检索词：{ideal_en_keywords}
建议 IPC 分类号：{ideal_ipc_codes}

请使用本地 Playwright 无头浏览器（生成 .js 脚本用 node 执行）访问以下站点进行检索：
1. Google Patents (https://patents.google.com/) - 搜索相关专利
2. arXiv (https://arxiv.org/search/) - 搜索相关论文
3. Semantic Scholar (https://www.semanticscholar.org/) - 补充学术文献

组合检索式建议：
- (核心术语1 OR 核心术语2) AND (patent OR specification)
- (英文术语1 OR 英文术语2) AND (algorithm OR method OR system)

要求：获取至少 8 篇精选文献（从 ≥20 条原始结果中筛选），每篇包含专利号/DOI、标题、链接。
```

### 策略 4：UI 截图强制导向

**适用 Stage**：UI 原型与 Playwright 截图（Stage 10）

**注入强度**：🔴 强制约束

**注入语气**：「必须围绕创新点生成可视化 UI 原型页面并使用本地 Playwright 无头浏览器截图，页面必须美观高清」

**注入指引**：
1. 从 Ideal 中提取「产品表现特征」和「GUI 可视化体现」内容
2. 从 Ideal 中提取「附图设计建议」的**四段式设计规范**（图面内容描述 + 关键元素 + 标注说明 + 产出物/联动要素），作为 HTML 页面生成的精确指导
3. 基于产品侧描述（4.1 节）的场景和步骤，设计包含 **8 类视图**的 HTML 页面：场景总览、场景 A 逐步、场景 B 逐步、产出物实例展示、状态转换/场景切换、创新点联动总览、方案对比
4. HTML 页面必须采用**现代 UI 设计风格**：圆角卡片、统一配色、清晰层次、中文友好字体
5. 使用本地 Playwright（headless 模式，`deviceScaleFactor: 2`，viewport ≥ 1440px）按步骤截图，确保高清输出
6. 每个场景的**每个步骤**必须有独立截图，场景间必须有切换示意截图
7. 生成 `figure_registry.json` 记录图号与截图的映射关系，通过 `figure_type` 区分产品侧和技术侧配图

**注入内容**：
- Ideal 中的「产品表现特征」章节（含场景列表、GUI 切换对比表、CLI 交互描述）
- Ideal 中的「附图设计建议」章节（含每张图的四段式设计规范：图面内容描述、关键元素、标注说明、产出物/联动要素）
- Ideal 中每个创新点的「GUI 可视化体现」描述
- **创新点与技术图的交叉引用映射**（从 Ideal 的创新点列表和技术架构章节提取，用于生成联动总览页和交叉引用标注）

**注入模板**（Stage 10 的 HTML 生成提示词中使用）：
```
请根据以下附图设计规范生成 HTML 原型页面：

{ideal_figure_designs}

每张图对应一个页面视图，页面视图之间通过导航栏切换。
页面必须采用现代 UI 设计风格（圆角卡片、统一配色、清晰层次）。

重要要求：
1. 场景逐步页的最后一步必须包含实际产出物预览区（以本发明主题自身的产出物为案例）
2. 必须包含产出物实例展示页（展示系统核心输出成果的高保真预览）
3. 必须包含创新点联动总览页（三列布局：GUI操作→后台处理→创新点）
4. 每张截图包含创新点角标和技术图引用标注
```

### 策略 5：评审对照清单

**适用 Stage**：专利评审（Stage 12）

**注入语气**：「检查是否充分覆盖」

**注入指引**：评审时请特别关注专利文档是否充分覆盖并突出了发明人指定的创新主题

### 策略 6：深度评审（四维检查 + 对抗性）

**适用 Stage**：专利评审（Stage 12，深度模式）

> **⚠️ 对抗性评审（强制）**：评审者必须找出至少 3 个实质性弱点和 1 个建设性改进方向。禁止所有检查项全部通过。

四维检查清单：

**A. 创新点覆盖率检查**
- 对照创新点清单，检查 4.2.2 核心算法流程中是否为每个创新点分配了独立的步骤组
- 每个步骤是否用自然语言把处理逻辑说清楚了

**B. 技术方案完整性检查**
- 检查专利 4.2.2 中是否用自然语言描述清楚了核心处理逻辑
- 不要求引用代码文件路径或函数名（专利中禁止出现代码引用）
- 确保技术方案的核心逻辑没有被遗漏

**C. 精简度检查（强制检查项）**
- 关键术语是否超过 6 个 → 如超过标记为 🔴
- 4.1 产品侧每个场景是否超过 4 步 → 如超过标记为 🔴
- 4.2 技术侧是否出现伪代码、函数名或代码路径 → 如有标记为 🔴
- 4.3 有益效果是否超过 3 段或超过 400 字 → 如超过标记为 🔴

**D. 举证充分性检查（新增，强制检查项）**
- 4.2.2 每个 S 步骤是否完整包含 6 个子段（问题动机、技术动作、输入数据样例、输出数据样例、关键参数、白话解释）→ 缺少任何子段标记为 🔴
- 每个核心创新点是否有至少一个专属 S 步骤提供举证 → 无专属步骤标记为 🔴
- 4.3 有益效果中的量化数据是否有推导过程 → 无推导标记为 🔴
- 4.2.3 和 4.2.4 是否与 S1-SN 高度重复 → 重复率超 50% 标记为 🔴
- 场景二描述深度是否与场景一对等 → 每步少于 80 字标记为 🟡

### 策略 7：修订保护性注入

**适用 Stage**：专利修订（Stage 13）

**注入语气**：「不要在修订过程中弱化或遗漏这些创新点」

### 策略 8：深度修订（素材库）

**适用 Stage**：专利修订（Stage 13，质量门禁重试时）

提供两类修订素材：

**素材 A：核心发明点技术方案参考**
- 从 Ideal 的 `## 三、发明内容 → 3.2 核心发明点详述` 提取
- 包含每个创新点的完整技术方案、伪代码、函数名、常量和调用链
- **强制约束**：撰写时必须提炼核心技术逻辑，用自然语言白话描述，禁止照搬伪代码

**素材 B：应用场景 Before/After 对比**
- 从 Ideal 的 `## 应用场景` 提取
- 如果 4.1.1 场景故事缺乏量化数据，从此处补充

**修订强制规则**：
1. S1-SN 每个步骤用自然语言把处理逻辑说清楚，不得留空
2. 禁止在专利正文中引用函数名或代码文件路径
3. 4.3 有益效果围绕核心创新点写 2-3 段 Before/After 对比，全节不超过 400 字
4. 禁止出现 LLM 工具调用痕迹
5. 防膨胀：产品侧不得超过 4 步，关键术语不得超过 6 个

### 策略 9：质量门禁评估导向

**适用 Stage**：质量门禁（Stage 14）

**注入语气**：「评估是否充分体现」

### 策略 10：严格质量门禁（阻断级）

**适用 Stage**：质量门禁（Stage 14，Ideal 可用时）

**阻断级检查清单（任一不满足则判定需修订）**：

1. **创新点覆盖**：文档必须覆盖全部 N 个创新点
2. **核心算法完整性检测**（最高优先级）：
   - 检查 4.2.2 中每个步骤（S1-SN），如果任何步骤的处理逻辑描述为空或仅有占位文本 → 必须修订
   - 步骤总数少于创新点数量 → 必须修订
3. **精简度检测**：关键术语>6个、步骤>4步、有伪代码/函数名、效果>400字 → 标注弱点
4. **量化数据覆盖**：Ideal 中的量化数字缺失超过 30% → 技术深度扣分
5. **参考文献完整性**：参考文献为空或少于 3 篇真实引用 → 必须修订
6. **技术图表完整性**：`$WORK_DIR/charts/` 下 PNG 文件 < 4 张 → 必须修订
7. **UI 截图完整性**：`patent_run/stage-08/screenshots/` 下无 PNG 文件 → 必须修订

### 策略 11：背景技术专项注入

**适用 Stage**：背景技术撰写（Stage 08）

**注入内容**：仅提取 Ideal 中与背景相关的部分：
- `## 二、背景技术` 章节内容
- `## 五、与现有技术的区别与优势` 章节内容

**注入指引**：
1. 围绕 Ideal 中列出的现有技术方案和技术演进进行展开
2. 确保 3.2 中的"不足"精确对标后续创新点要解决的问题
3. 引用 Ideal 中提到的具体量化数据和技术参数

## 三、深度结构化提取方法

从 Ideal 文档中提取特定结构的方法：

### 提取创新点完整技术描述

从 `## 核心创新点` 章节下的 `### 创新点 N：名称` 子节中，提取**完整 Markdown 内容块**（包括所有技术细节、代码证据、伪代码和量化数据），直到下一个 `### 创新点` 或 `##` 标题。

**注入到 `patent_content` 的 `{ideal_innovations}` 占位符**。

### 提取创新点名称列表

用于覆盖率检查。从 Ideal 中匹配 `### 创新点 \d+ [：:] (.+)` 模式。

### 提取量化数字

从创新点章节中提取：
- 4+ 位数字（如 60000、80000）
- 带单位的数字（如 30s、1200ms、80%）

用于量化数据覆盖检查。

### 提取应用场景

从 `## 应用场景` 提取 Before/After 对比，注入到 `{ideal_scenarios}` 占位符。

### 提取技术架构

从 `## 四、技术方案整体架构` 提取，注入到 `{ideal_architecture}` 占位符。

## 四、在智能体中的使用建议

### 无 Pipeline 模式（纯 SKILL.md 指导）

当智能体自行撰写专利内容时：

1. **Stage 01-02 产出的 Ideal 文档**作为全局上下文
2. 撰写关键术语（Stage 06）时 → 使用策略 2（软引导）
3. 撰写发明构思（Stage 07）时 → 使用策略 2（软引导）
4. **联网文献收集（Stage 05）时 → 使用策略 3.5（双语检索注入，强制联网）**
5. 撰写背景技术（Stage 08）时 → 使用策略 11（专项提取）
6. 撰写发明内容（Stage 09）时 → 使用策略 1（强制）+ 注入创新点/场景/架构
7. **UI 截图（Stage 10）时 → 使用策略 4（强制 Playwright 截图）**
8. 自我评审（Stage 12）时 → 使用策略 6（三维检查）
9. 修订（Stage 13）时 → 使用策略 8（素材库）
10. 质量门禁（Stage 14）时 → 使用策略 10（阻断级，含图文完整性）

### 有 Pipeline 模式（调用 orchestrate.py）

Pipeline 会自动处理 Ideal 注入。`orchestrate.py` 在调用 `execute_pipeline()` 时会将 `ideal_path` 注入到 `config.patent_ext`，Pipeline 内部的各 stage 会自动调用对应的注入函数。
